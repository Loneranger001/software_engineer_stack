# /understand — build a working model of an existing interface

> Path note: `<plugin-root>` is the directory containing this plugin's
> `plugin.json` (the plugin install root). All framework files referenced
> below live inside it.

The deliverable is understanding, not a document: a layered, source-referenced
explanation the user can interrogate until their mental model matches the code.
Everything learned lands in an **interface map** (`work/<id>/interface-map.md`)
that later stages — /document, /change-request, /intake — reuse instead of
re-investigating.

The defining rule is shared with /document: explain what the code DOES, not
what anyone (comments, wikis, the user, folklore) believes it does.

## 1. Locate and classify

1. Find the real entry points. The name the user gave may be a job name, a
   package, a script, an endpoint, or a business term — grep broadly
   (scheduler definitions, wrapper scripts, package specs, config/routing)
   and, if more than one candidate matches, confirm with the user which one
   they mean before investing in a trace.
2. Classify the interface type — **batch job | online/API | data pipeline |
   report/extract | library** — using the same emphasis map as
   `<plugin-root>/templates/understanding-doc.md`. The type decides
   where depth matters (a batch job's schedule and recovery, an API's entry
   points and error contract, a pipeline's lineage and restartability). The
   SAME type always gets the SAME emphasis, so explanations of different
   interfaces stay comparable.
3. Start `work/<id>/interface-map.md` from
   `<plugin-root>/templates/interface-map.md` and fill the identity
   section now. STATUS.md → `classify: done`.

## 2. Trace one real flow end-to-end

Read, don't skim. Signatures and comments describe intent; only the code
describes behaviour.

1. Follow the main path from trigger to final effect: scheduler/caller →
   entry point → every intermediate hop → outputs/side effects. Record each
   hop with `file:line`.
2. Where the environment is reachable (`$SES_DB_CONN`, `$SES_KSH_HOST`,
   `$SES_PY`), RUN things to confirm behaviour — queries, `--help`, dry-run
   modes, log inspection — and capture outputs to `evidence/`. Never execute
   anything with side effects on shared data.
3. Build the fact table in interface-map.md as you go: claim → source
   (`file:line` / query / run output). It is both the backbone of every later
   explanation and the resume point if the session dies.
4. Error paths are part of the flow, not an appendix: how failure surfaces
   (return codes, exceptions, alert/log tables), what state is left behind,
   and how the interface is restarted or recovered.

Accuracy rules (same as /research): every finding gets a source; inferences
are labelled `INFERRED` with their evidence and an open question to confirm;
when a name or comment disagrees with the code, the code wins.

STATUS.md → `trace: done`.

## 3. Map the dependencies both directions

Search **every repo in `<repo-set>`**, not just the one the interface lives
in (STATUS.md `repos-analyzed:`, else
`<plugin-root>/scripts/list-repos.sh <repos-folder>`). Consumers in a
sibling repo are the ones nobody remembers at change time — which is precisely
why they belong on the map.

1. **Upstream**: what feeds or triggers it — source tables/files, schedules,
   calling jobs/services, configuration it reads.
2. **Downstream**: what consumes or depends on it — grep for its outputs,
   its package/proc names, its file names, its table writes.
3. **Associated objects**: wrappers, shared packages, DDL, monitoring hooks.
4. Record the exact greps/queries used **per repo** so the map is reproducible
   — "nothing depends on this" requires showing the search that found nothing,
   in each repo it was run against. Qualify nodes and references with their
   repo (`<repo>:<path>:<line>`), and group the diagram's nodes by repo so a
   cross-repo dependency is visible as one.
5. Draw the mermaid dependency map in interface-map.md (upstream / interface /
   downstream subgraphs, labelled edges). Diagram and tables must agree in
   both directions — a node without a table row, or vice versa, is a gap.

STATUS.md → `map: done`.

## 4. Explain in layers

Present the interface in conversation, top-down, so the user can stop at the
depth they need:

1. **One paragraph** — what it exists to do, in business terms.
2. **At a glance** — trigger/schedule, inputs, outputs, key configuration.
3. **Flow walkthrough** — the mermaid flow plus a narrative of the main path.
4. **Dependency picture** — what feeds it, what would break without it.
5. **Failure & recovery** — how it fails, how you know, how it restarts.

Tie statements visibly to sources (`file:line` inline) — the references are
what lets the user trust the explanation and jump into the code themselves.
Label `INFERRED` items and open questions honestly: an admitted gap keeps
trust; a confident guess destroys it the first time the user checks.

If the user opened with a specific question, answer that first — with its
evidence — then offer the layers around it.

STATUS.md → `explain: done`.

## 5. Q&A until the model holds

Understanding is interactive; expect follow-ups and treat them as the point
of the exercise, not an interruption.

- Answer every follow-up from the code (or a fresh run), not from memory of
  your own summary; add each new fact to the fact table and, when it changes
  the picture, to the map's diagrams/tables.
- "What if" questions ("what happens if the feed is late", "what breaks if
  we rename this column") are answered by tracing the actual handling path;
  say clearly where the trace ends and reasoning beyond the evidence begins.
- Business meanings confirmed along the way go into
  `<work-repo>/.domain-glossary.md` (marked `from-code`, template:
  `<plugin-root>/templates/domain-glossary.md`) so the next task
  doesn't re-derive them.
- Findings that suggest work — bugs, dead code, risky patterns — go to
  PARKED.md and are mentioned to the user; never act on them here.

## 6. Close and hand off

1. Make sure interface-map.md reflects everything learned, including Q&A
   discoveries, and log remaining open questions in it.
2. Offer the natural next steps where they fit — a formal
   `/document understanding-doc` (its analyze stage reuses this map), a
   `/change-request`, or a full `/intake` — but don't push: understanding
   alone is a complete outcome.

## Fault tolerance

interface-map.md is written incrementally, fact table first. On interruption,
the next run reads STATUS.md and the map, and continues from the first stage
gate still pending — re-verifying nothing that already carries a source.
